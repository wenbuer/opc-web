# 执行引擎解耦设计（dsh → 可替换引擎）

> 目标：把「谁在执行角色任务」从控制台里剥出来，使 dsh 只是**其中一个实现**，
> 后续可接别的 CLI 引擎，或直连大模型 API 自建 agent 循环。

## Problem（为什么现在必须动）

控制台的角色执行完全长在 dsh 上，耦合散落在 8 个文件、103 处：

| 文件 | 处数 | 耦合内容 |
|---|---|---|
| `runner.py` | 51 | dsh 命令拼装、headless 子进程、会话日志解析（心跳/用量）、强杀 |
| `chain.py` | 18 | 调用 `run_headless_task`，注释与回退文本里写死 dsh 语义 |
| `server.py` | 14 | 技能扫描直接读 `~/.dsh/skills` 与 `profiles/*/node_modules` |
| `scheduler.py` | 12 | `_headless_text` 薄封装、路径注释 |
| `config.py` / `__main__.py` / `roles.py` / `agent.py` | 8 | 捆绑运行时、PATH 注入、文档字符串 |

后果：换引擎要动核心链路；想用 API 直跑得复制一套执行逻辑；两套并存时无法按用途分别配置。

## Decision（现在时：已落地的事实）

引入 `opc_web.engines` 包，**执行与事件流分离**：

```
chain / scheduler / server          ← 只说「跑这个 prompt，给我文本和用量」
        │  （只依赖 runner 的既有签名，零改动）
        ▼
      runner.py                     ← 事件缓冲 + 执行状态 + 三个入口（不含任何 dsh 细节）
        │  engines.get_engine()
        ▼
   engines/                         ← 接口层
     base.py    Engine 抽象、RunResult、Progress 数据类、能力声明
     dsh.py     DshEngine：dsh 命令、子进程、会话日志、心跳、用量、强杀、技能目录扫描
     api.py     ApiEngine：直连大模型 API 的 agent 循环
     registry.py 按配置选择；注册表 + 引擎自述（describe）
```

引擎接口（`base.Engine`）：

```python
class Engine:
    name: str = "base"
    def capabilities(self) -> dict:
        """{tools, streaming, usage, skills, sandbox} —— 控制台据此决定 UI 能力"""
    def preflight(self) -> tuple[bool, str]:
        """可用性自检：dsh 是否存在 / API key 是否配置，返回 (可用, 说明)"""
    def run(self, prompt, *, timeout=600, act="", cwd=None,
            on_progress=None) -> RunResult:
        """跑一次任务。on_progress(Progress) 在每次活动时回调（控制台据此推进度行）"""
    def kill(self, act) -> bool:
        """终止该 act 对应的运行（删除任务/超时用）"""
    def skills(self) -> list:
        """可选能力：该引擎能提供哪些可装配技能（无则返回空）"""
```

`RunResult` 统一承载：`text / usage / session / elapsed / killed / error`。
`Progress` 统一承载：`alive / elapsed / tools / lastTool / lastText / session`。

**关键不变式**：`runner.run_headless_task`、`run_headless_sync`、`emit`、`events`、
`exec_state`、`kill_spawn` 的**签名与语义全部保持不变**——调用方（chain/scheduler）零改动，
解耦对上层透明。

## Alternatives（被否方案与原因）

| 方案 | 为什么不用 |
|---|---|
| **保持现状，新引擎复制一套执行逻辑** | 两套逻辑并行维护，心跳/超时/用量口径必然分叉；上一轮 token 统计踩过的坑会重演 |
| **只抽一个 `run_prompt()` 函数，不做引擎对象** | 拿不到能力声明（有没有工具/流式/技能），控制台无法按引擎差异调整 UI 与提示词 |
| **按「CLI 引擎」与「API 引擎」写两套并行抽象** | 两者的差异集中在 run 内部，外层（进度/用量/超时/事件）完全同构，分两套等于重复外层 |
| **直接换成 API 实现，彻底弃用 dsh** | dsh 自带工具沙箱与技能生态，短期自建达不到同等能力；且现网执行链依赖它 |
| **引擎实现留在 runner.py，只在文件内加分支** | 51 处 dsh 细节与事件缓冲混在一个文件里，分支会越滚越大，等于没解耦 |

## Consequences（收益与代价）

**收益**
- 换引擎只动 `engines/`，chain/scheduler/server 不受影响
- 可**按用途分别配置**（如拆解用便宜快模型、执行用 dsh、triage 用 API），互不干扰
- 新引擎接入有明确施工面：实现 5 个方法 + 一次 preflight
- 能力声明让控制台能按引擎差异降级（无流式的引擎不显示进度行、无技能的引擎不显示技能页）

**代价（必须写）**
1. **多一层间接**：排错时要先确认「哪个引擎 + 哪次 run」，不能只 grep runner.py。缓解：`RunResult.error` 与事件里都带引擎名。
2. **抽象要覆盖两个真实实现才算数**：只接 dsh 时接口是假设，`ApiEngine`（阶段 2）落地前，接口设计可能仍需调整。
3. **搬运期有回归风险**：dsh 实现从 runner 移入 `engines/dsh.py`，绑定的是同一批测试（92 项）；搬运必须保持全绿，否则回滚。
4. ~~技能扫描暂不迁~~（阶段 4 已解决）：技能源改为引擎自报 `skills()` —— DSH 列本机已装技能，API 引擎明确为空，技能页不再与引擎打架。
5. ~~回退语义要人为定义~~（阶段 5 已定，见下）：默认 `api` 兜底 `dsh`；触发边界严格限定在「引擎侧失败」，
   配置错误（引擎名写错）仍然直接报错、不会被回退掩盖。

## 配置

`opc-config.json`（或同名环境变量）：

```json
{
  "engine": "api",
  "engineFallback": "api",
  "engines": {
    "dsh":  { "command": "", "profile": "headless" },
    "api":  { "provider": "deepseek-official", "model": "", "baseUrl": "", "apiKeyEnv": "DEEPSEEK_API_KEY" }
  }
}
```

- `engine` 为空时默认 `api`（不依赖 dsh）；改成 `dsh` 即回到解耦前的执行方式
- 设置页可写：`engine` 在 `config.SETTING_KEYS` 白名单内，取值必须已注册（写错当场 400）
- `engineFallback` 默认 `api`：主力 dsh 没跑起来时用直连 API 兜底（触发边界见阶段 5 说明）；
  写空字符串 = 关闭回退，环境变量 `OPC_ENGINE_FALLBACK` 优先

## 验证口径

- 阶段 1 完成后：`python -m unittest discover -s tests` 全绿（含新增引擎接口测试）
- 行为等价抽查：同一 prompt 经 `DshEngine` 与解耦前 `runner.run_headless_task` 返回同形结果
- `config.ENGINE` 切到不存在的引擎名时，`get_engine()` 必须报错而非静默回退（防配置错误被吞）

## 阶段 2 落地说明（ApiEngine）

实现位置：`src/opc_web/engines/api.py`（标准库 urllib + SSE 流式，**未引入新依赖**）。

能力：tools / streaming / usage / sandbox 四项为真，skills 为假——控制台据此降级技能面板。

agent 循环：system prompt（执行角色工作方式）→ 用户 prompt → 模型返回 tool_calls →
本地执行（list_dir / read_file / write_file / run_command）→ 结果回传 → 循环，
直到模型给出纯文本结论；上限 maxSteps（默认 40，防空转烧钱）。

| 维度 | DshEngine | ApiEngine |
|---|---|---|
| 进度来源 | 会话日志轮询（2s/次，三重校验认领会话） | API 流式增量（真流式，1s 节流） |
| 用量来源 | 会话日志最后一条 assistant usage | API 返回的 usage（含 prompt_cache_hit_tokens） |
| 工具集 | dsh 内置全套 + 技能生态 | 本项目实现的 4 个基础工具 |
| 技能 | 支持 | 不支持 |
| 沙箱 | dsh 自带 | 路径 resolve 后必须落在项目根内；命令限时 |

验证：tests/test_api_engine.py 9 项（沙箱越界拒绝、单轮文本、工具调用轮、循环上限、取消、缺 Key）。
端到端实测：直连 API 3.0s 完成「列目录 + 总结」，工具调用 1 次、进度回调 4 次、用量 input 1379 / output 154。

测试抓到的真 bug：run() 开头曾清空取消标志，导致 kill() 先置位再被清除、取消失效；改为只在 finally 清理。

## 阶段 3 落地说明（进度统一 / 配置连通 / 设置页）

**进度通道统一**：`Engine.run(on_progress=)` 曾经没人接管 —— dsh 的进度由 `_watch_session`
直接写 `_EXEC_STATE`，api 引擎的 `on_progress` 回调永远不触发（`if on_progress:` 恒假），
切到 api 后工作台看不到任何实时进度。现在 runner 提供 `_progress_sink(act)`：

```
引擎（dsh / api）──on_progress(Progress)──▶ runner._progress_sink ──▶ _EXEC_STATE + exec/progress 事件
```

两个入口（`run_headless_task` / `run_headless_sync`）都把回调接上，`_watch_session` 改为
经回调外报（未接回调时回退本地写法，行为不变）。`_EXEC_STATE` 重新成为进度的唯一出口。

**配置连通**：`ApiEngine._cfg()` 原先只读 `opc-config.json` 的 `engines.api` 段，而设置页写的
是 `model` 段 —— 界面选了自定义提供方，引擎还去打默认端点。现在 `model` 段打底、
`engines.api` 覆盖（要按引擎单独配便宜模型时才用它）。

**自述与设置页**：`registry.describe()` 给出「当前是谁 / 能不能用（preflight）/ 有什么能力 /
还能换成谁」，新增 `GET /api/engines`，设置页「执行引擎」区直接展示并可切换；切换写盘后
`config.reload()` 重算 `ENGINE`，**立即生效无需重启**。`OPC_ENGINE` 环境变量优先于设置页
选择，`describe()` 会带 `envOverride` 让界面说明白，避免「切了没反应」。

**默认引擎改为 api**：新装即用，不再要求先装 dsh；dsh 作为可选项保留（本机已装时
`preflight` 会确认命令可用）。

**顺带修掉**：`registry._load_builtins()` 曾用 `except: pass` 吞掉内置引擎的导入异常 ——
api.py 一旦导入失败，引擎会凭空消失、只在切过去时报「未注册」。现在记录到 `load_errors()`
并在取用时报出原始原因。

## 阶段 4 落地说明（dsh 搬家 / 技能随引擎 / 按用途路由）

### dsh 实现搬进 `engines/dsh.py`

原先「阶段 1 暂寄 runner」的 12 个函数（命令拼装、子进程、会话日志、心跳、用量、强杀）
全部迁入 `engines/dsh.py`（现 472 行 / 16 个函数）。搬运不是剪切粘贴，有三处接口化改造：

| 原来的写法 | 现在的写法 |
|---|---|
| `_watch_session` 直接写 `runner._EXEC_STATE` | 只调 `on_progress(Progress(...))`，状态由 runner 的 sink 落 |
| `_spawn_headless` 读 `_EXEC_STATE[act]["beatMono"]` 判存活 | 读自己的 `_BEAT[act]`，不再反向依赖 runner |
| 跑完由 `_spawn_headless` 清 `_EXEC_STATE` | 报一次 `Progress(finished=True)`，由 sink 清 |

结果：**runner 从 478 行降到 130 行，只剩事件缓冲、执行状态、三个入口**
（`run_headless_task` / `run_headless_sync` / `kill_spawn`），一个 dsh 名字都没有。

### 技能随引擎（`skills()` 落地）

`server.py` 原来自己扫 `~/.dsh/skills` 等三处目录 —— 换成 API 引擎后照样读 dsh 的技能，
技能页与正在跑的引擎对不上。现在扫描逻辑归 `DshEngine.skills()`，
`/api/engine-skills` 问当前引擎要清单（旧名 `/api/dsh-skills` 保留兼容），
API 引擎返回空并附一句「切到 DSH 引擎后可用」。实测：api 引擎 0 条、dsh 引擎 41 条。

### 按用途路由

```json
{ "engine": "api", "engineFor": { "prompt": "api", "execute": "dsh" } }
```

- `config.engine_for(purpose)`：`engineFor.<用途>` 优先，留空回退主引擎；
- 三处调用点接上用途：拆解（chain，`prompt`）、汇总/日报/知识沉淀（scheduler，`prompt`）、
  角色任务执行（chain，`execute`）；
- 路由带来一个真问题：**同一个 act 由哪个引擎在跑，kill 时得知道**。
  现在 `run_headless_task` 登记 `act → 引擎名`，`kill_spawn` 先查表、查不到再逐个引擎问。
  为此 `ApiEngine.kill` 改为只回答「现在是否真的有在跑」（原来恒返回 True，
  多引擎下会让上层误以为已经杀掉了）。

## 阶段 5 落地说明（回退策略）

**默认方向：api 兜底 dsh**。DSH 是主力（工具沙箱 + 技能生态），它没跑起来时用直连 API 顶上，
避免整条执行链卡死在一个引擎上。主引擎本身就是 api 时没有备用 —— 自己兜自己无意义。

**触发边界**（`runner._engine_failed`）：只回退「引擎侧失败」，绝不回退「任务没做完」。

| 情况 | 回退？ | 为什么 |
|---|---|---|
| 引擎报错（没装 dsh / 鉴权失败 / 启动异常） | 是 | 换引擎确实能救 |
| 秒退无产出（耗时 < `fallbackMaxElapsed`，默认 60 秒） | 是 | dsh 秒退（T-006 那种）属引擎侧问题 |
| 跑了很久仍无产出 | 否 | 那是任务本身的问题，两个引擎会跑同样久；重跑 = 重复劳动 + 重复烧钱 |
| 被取消 / 超时主动停 | 否 | 重跑等于把刚停掉的活又拉起来 |

**留痕**：回退会发一条 `engine/fallback` 事件（`from` / `to` / `reason`），
工作台详情能看到「谁失败了、换成了谁、为什么」。

**实测**（把 dsh 命令指向不存在的可执行文件，模拟「没装 dsh」）：

```
主引擎: dsh | 备用: api
回退留痕: {'purpose': 'execute', 'from': 'dsh', 'to': 'api', 'reason': '0 秒退无产出'}
跑完执行状态: {}          # 无残留
文本: 当前目录是一个名为 OPC 的项目根目录…     # 备用引擎真的把活干完了
```

**顺带修掉的真 bug**：这次实测暴露出 `ApiEngine` 跑完**不报结束信号**，
`exec_state` 会一直留着「执行中」的残影（工作台上表现为任务结束但进度行不消失）。
现在两套引擎的 `run()` 都在返回前报一次 `Progress(finished=True)`，
并把这条写进 `Engine.run` 的接口契约（`base.py`）。
