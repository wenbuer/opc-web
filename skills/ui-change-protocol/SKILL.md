# 界面改动协议

## 1. 先出静态预览，再实现

用户明确要求过：「下次先出示意图，我挑完再改」。

做法：探针页注入 DOM + 引用**真实 main.css** → 截图，**不动产品代码**。
UI 返工是本项目最贵的浪费：看板改版试了 3 版、悬浮球改了 5 轮、日志入口加了又删。

## 2. 先声明影响面

一句话说清动的是哪个视图/面板、碰不碰数据层。方向错了用户能立刻拦住。

**语义对不上就当场说，别先实现再解释。** 用户说「把 X 放到 Y 上」时，先确认 X 在 Y 上还有没有
意义 —— 如果放过去就得替它重新编一个含义，那不是实现问题，是需求问题，先说再动。
实例：要求把「立即执行」放到子任务上，而子任务脱离不了任务（执行链按任务走、一次一个任务），
只能把它解释成「让父任务跑」—— 一个名不副实的按钮。当时我实现了、再在汇报里解释，
用户的反馈是「这种情况你需要提前和我说」。**这类要重新解释语义的改动，先问再做。**

## 3. 一次改完

不要「改一半 → 跑一次 → 再改一半」。块结构文件（CSS / JSON）尤其要整块处理。

本会话 5 次半成品编辑全出在这里：`chunks` 改名漏改、`bars` 赋值顺序、CSS 按行删、`finished` 顺序、`activeSub` 提示。

## 4. 验证分档

| 改动性质 | 验证手段 |
|---|---|
| 逻辑 / 状态（拖拽、过滤、跳转） | **文本断言**（探针打印结论） |
| 布局 / 视觉 | 截图 |
| 数据结构 / 后端 | 跑测试 + 断言字段 |

## 5. 主动报告不确定处

截图只能证明「渲染出来了」，不能证明「交互对了」。分不清就说分不清，别把推断说成验证。

## 6. 改完即快照

每轮改动 `git add -A && git commit`（嵌套仓库分别在各自目录 commit）。用户说「回退」时才有得回。
